# SBoB Attack Matrix — redis kill-chain vs generated detection bundle

M3 exit-criteria deliverable (issue #4), extended with the M4 rulePolicies
signature rules (issue #5): the 62-attack kill-chain suite from
the upstream SBoB reference (`docs/upstream-redis-attacks.yaml`,
k8sstormcenter/bob `example/redis-attacks.yaml`) mapped against the rules
generated by `sbobctl transpile --sbob sbobs/redis.yaml --target k8s-node`.
Machine-checked on every build by `scripts/attack-false-negative-check.ts`
(TDS 11.3): each attack must be detected by a rule id or carry a documented
blind/partial class.

## Coverage classes

- **EXEC** — detected as undeclared process execution (100011).
- **OPEN** — detected as undeclared file open (100021); often co-fires with EXEC.
- **CONNECT** — detected as undeclared egress (100031); depends on the saddr
  decoder work item (TDS 7.3.1) to emit sbob.dst_ip/sbob.dst_port.
- **BLIND-L7** — in-process RESP/Lua commands: no syscall leaves the
  redis-server process, so node auditd sees nothing. This is the declared L7
  boundary (SBoB `endpoints[]` semantics); L7 coverage is the M6–M7 scope.
- **DNS-NAME** — the observable signal is a DNS *name*, not an address; node
  auditd telemetry cannot see query names, and port 53 is in the egress
  allowlist. Windows agents cover this via Sysmon EID 22 (rule 100007); on
  k8s nodes it stays blind until an agent-side DNS tap is designed.
- **M4-PENDING** — capability/syscall-level signal still pending: bpf and
  mount have no rulePolicies signature rule yet (the four M4 audit-keyed
  policies cover init_module, unshare/setns, ptrace, memfd_create); the
  100011 detection is the process-level fallback that fires today.
- **FILELESS-EXE** — memfd-based execution reports `exe=/proc/self/fd/N`;
  100011 still fires (path not in execs[]) but the process identity is opaque.
- **K8S-API** — control-plane API access: the connect-side overlay (100003)
  and the manager-side JSON rule (100064) cover it since M4, alongside the
  node-side process/egress footprint.
- **SIG** — a rulePolicies signature rule (TDS 7.4) fires on the
  security-relevant primitive itself (module load, namespace change, ptrace,
  memfd, k8s API), not only on the process-level exec footprint.

## Scorecard

- Node-telemetry footprint detected (100011/100021/100031, level 9, every
  alert attributed): **44 / 62 (71%)** — includes partial classes below.
- BLIND-L7 (in-process RESP/Lua, no syscall leaves redis-server): **18 / 62**
  — declared boundary; the SBoB model treats in-protocol commands as
  `endpoints[]` scope, addressed by the L7/M6–M7 work, not by node audit.
- DNS-NAME component blind on k8s: **3 / 62** (rows 22, 23, 25 — the exec is
  caught, the DNS *name* is not; Windows agents: EID 22 rule 100007).
- Capability/syscall-level signal (M4 rulePolicies): rows 51 (init_module),
  60 (ptrace), 59 (unshare/setns), 7 (memfd_create) and 50 (k8s API connect
  + manager JSON rule) now carry syscall-level signature rules (100060-100064,
  100003). Remaining at process-level fallback only: **2 / 62** — rows 52
  (bpf) and 54 (mount); row 32 (`MODULE LOAD`, in-process dlopen) remains
  BLIND-L7 — dlopen is a library call, not init_module, so no auditd key
  covers it.

## Notes

- The corpus' `exec-from-data-mount` only fires 100021 when /data is writable
  on the image — the upstream probe itself expects the read-only case.
- `MODULE LOAD` performs the dlopen inside the redis-server process: no
  exec event exists to detect; this is an `endpoints[]`/capabilities matter
  (M4), not a codegen gap.
- Lab replay: `scripts/logtest-corpus.sh k8s` (corpus:
  `test/corpus/redis-{benign,drift}.k8s.audit`).
